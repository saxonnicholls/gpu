Detailed Description

snicholls::gpu::cuda_training_backend: snicholls-core's batched training passes on an NVIDIA GPU with every step on the device, so a training step's data stays there.

Overview. Core's batched passes (ml::block_forward_sequence, ml::block_backward and the attention, MLP and linear passes beneath them) make every step a call with their backend (core's TRAINING.md T9): the products, and fill_rows, copy_rows, add_rows, add_bias_rows, sum_rows, mlp_activate_rows and its backward, block_norm_rows and its backward, the four attention steps, and linear_heads with its backward (the keys' and values' projections as one product and a permutation, not one per head). This header overloads each for cuda_training_backend, so with the weights, activations and gradients in device_buffers the whole step runs on the GPU: the products by cuBLAS, the other steps by kernels compiled at run time (NVRTC, to the device's machine code) when cuda_kernels is created.

  • cuda_kernels::create(context): compiles the kernels for the context's device; result with a cuda_failure.
  • cuda_training_backend{{&context}, &kernels}: the backend, two pointers.
  • adamw_segments(backend, p, g, m, v, step, config, segments, grad_scale): AdamW over many tensors laid end to end, each with its own weight decay, in one launch, the clipping factor folded in.

const gpu::cuda_training_backend device{{context.get()}, kernels.get()};
// Every tensor once on the host and once on the device
struct tensor {
std::vector<float> host;
std::unique_ptr<gpu::device_buffer<float>> dev;
};
std::vector<tensor> t;
auto make = [&](std::size_t size, float scale, float offset) {
tensor x{std::vector<float>(size), nullptr};
for (std::size_t i = 0; i < size; ++i)
x.host[i] = offset + scale * std::sin(0.37f * static_cast<float>(i) + static_cast<float>(t.size()));
x.dev = std::make_unique<gpu::device_buffer<float>>(*context, size);
x.dev->upload(x.host);
t.push_back(std::move(x));
return t.size() - 1;
};

auto run = [&](const auto& backend, bool on_device) {
auto s = [&](std::size_t i) { return on_device ? t[i].dev->span() : std::span<float>(t[i].host); };
using W = ml::dense_weights<float>;
ml::block_weights<W> w{};
w.norm1_weight = s(n1w), w.norm1_bias = s(n1b), w.norm2_weight = s(n2w), w.norm2_bias = s(n2b);
w.attention = {W{s(wq), d, d}, W{s(wk), d, d}, W{s(wv), d, d}, W{s(wo), d, d}, s(bq), s(bk), s(bv), s(bo)};
w.mlp = {W{s(up), f, d}, W{}, W{s(down), d, f}, s(bup), {}, s(bdown)};
const ml::block_activations<float> act{s(x0), s(h1), s(x1), s(h2), {s(q), s(k), s(v), {}, {}, s(y), s(lse)}, s(aup), {}, s(hid)};
ml::block_forward_sequence<c>(backend, w, s(xs), ml::no_rope, act, sequences); // the batch in one call
};
run(device, true); // the norms, residuals, activation and products on the GPU
run(snicholls::linalg::reference, false); // core's reference on the host copies
std::vector<float> got(n * d);

A batch of sequences. Core's passes take a number of sequences laid end to end (one call per layer for a whole batch); every overload here takes it too. The row-wise steps and the products run over all the rows at once (linear_heads one product and one permutation into each sequence's block of keys and values); QK norm and RoPE one launch over every (row, head), positions restarting in each sequence; flash attention one launch per kernel, the sequence the grid's z; the matrix-product and tiled attention paths one sequence after another.

Core's optimisers run here too: adamw_rows has its kernel, and ml::muon_step (core's ml/muon.hpp), whose every step is a call on the backend, runs on the device through the overloads here: the momentum and the update by scale_rows, add_rows and copy_rows, the norm by sum_squares, and the Newton-Schulz iteration's three products per step through gemm, so in bfloat16 under cuda_math::bf16, as nanochat runs it.

// Muon on a weight matrix in device memory: every step of core's ml::muon_step (the momentum, the norm, five
// Newton-Schulz iterations, the update) on the GPU, the products by cuBLAS (bfloat16 here, as nanochat's)
gpu::cuda_training_backend bf16 = device;
bf16.math = gpu::cuda_math::bf16;
const std::size_t rows = 128, cols = 512;
gpu::device_buffer<float> mw(*context, rows * cols), mg(*context, rows * cols), mm(*context, rows * cols),
mwork(*context, ml::muon_work_size(rows, cols));
std::vector<float> hw(rows * cols, 0.0f), hg(rows * cols);
snicholls::stats::wyrand rng(7); // a full-rank gradient
for (float& x : hg)
x = static_cast<float>(2 * snicholls::stats::uniform_real(rng) - 1);
mw.upload(hw);
mg.upload(hg);
gpu::fill_rows(device, mm.span(), 0.0f); // the momentum starts at zero
ml::muon_step(bf16, mw.span(), std::span<const float>(mg.span()), mm.span(), rows, cols, ml::muon_config<float>{}, mwork.span());
mw.download(hw);

Relationships. cuda.hpp (the context, the products, device_buffer), core's ml/transformer_block.hpp, ml/attention_layer.hpp, ml/mlp.hpp, ml/linear.hpp (the operations it overloads and the reference it is checked against). Group: snicholls-gpu.

Implementations. The elementwise steps (and AdamW, and the bfloat16 conversion) four elements a thread through float4 when every pointer is 16-byte aligned, one a thread otherwise, the same arithmetic either way; the norms a warp per row (each lane's part of a row's sums in order, then the lanes in a fixed order), the backward pass recomputing the row's statistics in the same kernel; the column sums (sum_rows, the norms' weights' and biases' gradients) a block per 32 columns, 32 row groups each summing its rows in order and then the groups in order; the embeddings' backward a block per token, the first token of each id adding that id's rows in token order; the classifier a warp per row with the maximum and the sum of exponentials in one online pass. Nothing is atomic, so the result does not depend on scheduling; the activations with core's formulas in float. Attention under cuda_math::tf32, for heads of 32 or 64 channels, is flash attention on the tensor cores (mma.sync m16n8k8, TF32 in, float accumulated, as FlashAttention-2 without atomics): the forward a block per (64 queries, head), the online softmax in registers, the log-sum-exp saved, no n x n scores, the tiles past the diagonal or outside a window skipped; the backward one kernel for the queries' gradients and one for the keys' and values' (a block per 64 keys walking the queries that see them, a group's heads in order), both recomputing the probabilities. Otherwise, up to cuda_training_backend::gemm_attention_max tokens (4096), is matrix products head by head, as llm.c's: the scores S = Q Kᵀ through cuBLAS (the tensor cores under TF32), a softmax kernel writing the log-sum-exp, Y = P V; the backward recomputes P from the log-sum-exp and makes the four gradient products, a group's heads adding into its keys' and values' gradients in order. Longer sequences take tiled kernels for heads of 16, 32, 64 or 128 channels: a thread per query or key with its row in registers, the other side through shared memory a tile at a time, the keys' gradients split over the queries into partials added in a fixed order; other head sizes, up to 256, a warp per (token, head). Every path is deterministic. QK norm and RoPE one thread per (token, head), the norms' weight gradients summed in core's order. The kernels' working space (cuda_kernels::scratch, cuda_kernels::partials) is kept between calls, so a step allocates nothing and, apart from sum_values and sum_squares (which return a number to the host), waits for nothing: a whole forward and backward pass can be captured as a cuda_graph and replayed.

Guarantees. Every step is enqueued on the context's stream, in the order the pass makes them, after the previous product; the results agree with core's reference to rounding (the device's expf, tanhf, sqrtf differ from the host's in the last bits). One training step at a time per context.

Errors. cuda_kernels::create returns a cuda_failure (with the compiler's log on stderr) if the kernels do not compile. A launch or copy that fails throws cuda_exception.

Performance. benchmarks/cuda_ops_benchmark.cpp: a GPT-2-small layer's training step with its data on the device, against the same step staged; see BENCHMARKS.md. A whole GPT-2 small step (124M parameters, sequences of 1024 tokens, forward, backward, clipping and AdamW) on an RTX PRO 4000 Blackwell with nothing else on it, 2026-11-17, with cuda_math::tf32: 68.7 ms at batch 1 and 230 ms at batch 4, against llm.c's 34 and 105 ms in bfloat16; 424 ms at batch 4 in float. At batch 4: the products 131 ms, flash attention 46 ms (115 ms as matrix products), the rest 57 ms. After 0.5.0 (same device, CUDA 13.3, Release, 2026-11-17, shared with another training job, so the shortest of eleven steps per launch): the kernels other than the products and attention 70 ms to 47 ms a step at batch 4 in bfloat16 (AdamW in one launch with the clipping folded in, the classifier 14 to 11 ms, the norms' parameter gradients 7.2 to 0.8 ms, sum_rows 5.6 to 2.0 ms, the embeddings' backward 3.7 to 0.8 ms, the norms' backward without its third kernel, allocation and wait).

One Muon step over a GPT-2-small block's four matrices (768 x 2304, 768 x 768, 3072 x 768, 768 x 3072; 7.1M parameters, about 127 GFLOP of Newton-Schulz products) on the same device, 2026-11-17, Release, while a training run kept the GPU about 98% busy (so upper bounds): 29.8 ms with float products, 15.6 ms in TF32, 12.1 ms in bfloat16, against 2.0 ms for adamw_rows on the same matrices.

Tests and demos. tests/cuda_ops_test.cpp (each step against core's, and whole training steps of GPT-2-, Llama- and nanochat-shaped blocks against the reference; Muon's step in float, TF32 and bfloat16), demos/cuda_ops_demo.cpp.

Dependencies. cuda.hpp, <nvrtc.h>, core's ml/transformer_block.hpp. Link CUDA::nvrtc too.

Known issues. Float only (the products can be TF32). The attention's products are one call per head; its scores take 3 n² floats of scratch. The tiled kernels for long sequences run on the CUDA cores, not the tensor cores.

Status. Experimental, new in 0.2.0.

One AdamW step over many tensors laid end to end in one flat span, each with its own weight decay, in one launch (one per 32 tensors): core's adamw_step on every element, the bits of adamw_rows per tensor.

A model's parameters, gradients and moments are usually each one allocation, the tensors at fixed offsets; calling adamw_rows per tensor is one launch each (sixteen for GPT-2), this is one. The gradient can be scaled first (grad_scale, 1 by default and then exact): gradient clipping's factor folded into the update instead of a pass of its own over the gradients, with the bits of scale_rows followed by the update.

Parameters

std::invalid_argumentif the sizes do not add up; cuda_exception if a launch fails.

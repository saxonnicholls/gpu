Detailed Description

snicholls::gpu::opencl_device_backend: core's forward passes with every operand in device memory on an OpenCL 1.2 device, through opencl_arena, device memory addressed by host-shaped spans.

Overview. opencl_backend copies its operands to the device for each product; a model's weights then cross the bus on every call, and everything but the products runs on the host. This backend keeps everything on the device: the weights, the activations, the key-value cache. OpenCL 1.2 (all macOS offers its GPUs, and what PoCL runs) has no pointers a host can hold, so opencl_arena reserves a range of virtual addresses that no page backs and gives out spans inside it; a span's address is its place in a device buffer (locate). Core's passes take spans, slice them and hand them to the backend's operations, which are overloaded here for opencl_device_backend (found by argument-dependent lookup), as cuda_ops.hpp overloads them for CUDA's device pointers: the same core code runs on both. A host read of device memory faults at once rather than reading garbage.

The operations, forward only (inference and evaluation), from one kernel source written for OpenCL and CUDA (detail/rows_source.hpp):

  • products: gemm (and through it ml::linear_sequence, ml::linear_heads) with opencl_context's kernel over device buffers (gemm_buffers), gemv as one column;
  • rows: fill_rows, copy_rows, add_rows, add_bias_rows, embed_rows, block_norm_rows (RMS and layer norms), mlp_activate_rows (SwiGLU), attention_position_rows (QK norm and RoPE), attention_attend_rows (each sequence's causal attention, windowed or not), cross_entropy_rows, sum_values, sum_squares;
  • the key-value cache: kv_store_rows and attention_attend_cached_rows, and heads_from_rows (a projection's rows as heads, for weights core's linear_heads does not take), the operations a forward pass over new tokens needs beside core's (their host reference is in the consumer's model, training/llama.hpp, until core has them).
const auto arena = gpu::opencl_arena::create(*context, std::size_t{1} << 30, std::size_t{16} << 20);
const gpu::opencl_device_backend b{context.get(), arena.get(), kernels.get()};
// Host values to device spans: the spans are addresses in the arena, as core's passes take them
const auto up = [&](const std::vector<float>& v) {
auto s = arena->allocate<float>(v.size());
arena->write(s, std::span<const float>(v));
return s;
};
constexpr ml::transformer_config c{.d_model = 32, .n_heads = 4, .n_kv_heads = 2, .head_dim = 8, .d_ff = 48, .norm = ml::norm_kind::rms,
.norm_eps = 1e-5, .mlp = ml::mlp_kind::swiglu, .rope = ml::rope_kind::half, .rope_base = 10000};
constexpr std::size_t n = 12, d = c.d_model, qn = c.q_size(), kn = c.kv_size(), f = c.d_ff, h = c.n_heads;
const auto n1 = values(d, 1, 1), n2 = values(d, 2, 1), wq = values(qn * d, 3), wk = values(kn * d, 4), wv = values(kn * d, 5), wo = values(d * qn, 6),
wg = values(f * d, 7), wu = values(f * d, 8), wd = values(d * f, 9), x = values(n * d, 10);
using W = ml::dense_weights<float>;
const auto weights = [&](auto&& at) {
ml::block_weights<W, float> w{};
w.norm1_weight = at(n1), w.norm2_weight = at(n2);
w.attention.q = W{at(wq), qn, d}, w.attention.k = W{at(wk), kn, d}, w.attention.v = W{at(wv), kn, d}, w.attention.o = W{at(wo), d, qn};
w.mlp.gate = W{at(wg), f, d}, w.mlp.up = W{at(wu), f, d}, w.mlp.down = W{at(wd), d, f};
return w;
};
const auto acts = [&](auto&& alloc) {
ml::block_activations<float> a{};
a.x0 = alloc(n * d), a.h1 = alloc(n * d), a.x1 = alloc(n * d), a.h2 = alloc(n * d);
a.attention.q = alloc(n * qn), a.attention.k = alloc(n * kn), a.attention.v = alloc(n * kn), a.attention.y = alloc(n * qn);
a.attention.lse = alloc(n * h), a.mlp_up = alloc(n * f), a.mlp_gate = alloc(n * f), a.mlp_hidden = alloc(n * f);

};

acts([&](std::size_t m) { return arena->allocate<float>(m); }));
std::vector<float> got(n * d);
arena->read(std::span<const float>(dx), std::span<float>(got));

Relationships. opencl.hpp (the context and its product kernel), cuda_ops.hpp and cuda_rows.hpp (the same operations on CUDA), core's ml/ passes. Group: snicholls-gpu.

Implementations. One. RoPE's table stays the caller's host memory (a rope_source): its rows for a call are copied up, as cuda_ops.hpp does.

Guarantees. Products: core's reference bits (the kernel of opencl.hpp, each output summed in index order), except products of at most matvec_max rows (a decode step), which run a work-group an output and add 64 partial sums by a fixed tree: within |Δ| ≤ k 2^-23 Σ_p |x_p w_p|, as gpu's quantised matrix-vector kernel. Norms, QK norm, RoPE and the cache's writes: core's operations in core's order, one work-item a row or head; they differ from the host only by the device's exp, log and sqrt (OpenCL's are within a few ulp, not correctly rounded). Attention and the cross-entropy share their reductions across a work-group in a fixed order (lanes merged in order, a fixed tree), so they differ from core's sequential sums by rounding; every result is deterministic. Measured against the host on real models in snicholls-ml's PLAN.md. The backend is trivially copyable (three pointers); opencl_arena and opencl_device_kernels serve any number of threads (launches are serialised).

Errors. opencl_exception for a failed OpenCL call; std::invalid_argument for a span not in the arena; std::bad_alloc when the arena's reservation or the device is exhausted; std::logic_error for the BLAS operations a forward pass does not use (dot, axpy, syrk, triangular_solve).

Performance. Measured in snicholls-ml's PLAN.md (prefill and decode against llama.cpp on the same machine).

Tests and demos. tests/opencl_device_test.cpp (every operation against core's host reference, a whole block's forward pass, the cache), demos/opencl_device_demo.cpp.

Dependencies. OpenCL 1.2, <sys/mman.h> (the reservation), core's ml/ headers.

Known issues. Heads of at most 128 channels in attention. The backward operations are not here (training on OpenCL keeps opencl_backend). On macOS's AMD driver (Radeon Pro Vega II, macOS 26) a pair of small buffers made and released for every call (RoPE's rows, at first) got the process killed by the driver after some thousands of calls, deterministically for a given run; the backend now writes such data into buffers it keeps (rope_rows, the quantised products' scratch) and retires a buffer it outgrows until the queue has run. Another GPU client at the same time (llama.cpp's Metal backend offloads large products even with -ngl 0) has also stopped runs.

Status. Experimental.

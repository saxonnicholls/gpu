Detailed Description

snicholls::gpu::cuda_quant_kernels: matrix products whose weights stay in core's quantised formats in an NVIDIA GPU's memory, dequantised in registers, forward and backward to the input, on the CUDA cores or the tensor cores.

Overview. The CUDA counterpart of opencl_quant.hpp, from the same kernel source: weights in ggml's Q8_0, Q4_0 or MXFP4 blocks (ml/quantize.hpp), QLoRA's NF4 (ml/nf4.hpp) or dense bfloat16, float16, FP8 E4M3 or E5M2 (ml/minifloat.hpp), read in place from device memory and dequantised as the product needs each weight. Core's operations are overloaded for cuda_training_backend (found by argument-dependent lookup), with every span device memory, so core's ml::lora_sequence and ml::lora_sequence_backward run a QLoRA layer entirely on the GPU:

  • linear_sequence(b, w, xs, ys, bias): Y = X Wᵀ + b, float activations.
  • linear_sequence_backward_input(b, w, dys, dxs): dX += dY W (the base is frozen: no weight gradient).
  • linear_sequence_q8(b, w, xs, ys, bias): the activations quantised on the device to the 8-bit blocks core's dot product pairs the weights with (Q8_0 for Q8_0, Q4_0, MXFP4, Q5_0; Q8_1 for Q4_1, Q5_1; Q8_K for Q2_K to Q6_K, TQ1_0 and TQ2_0), and core's integer block dot products.

w is core's view (ml::quantized_weights<Block>, ml::nf4_weights, ml::dense_weights<S>), or a block_weights<Block> of Q4_1, Q5_0, Q5_1, NVFP4, Q1_0, Q2_0, Q2_K to Q6_K, TQ1_0, TQ2_0, the IQ family (IQ1_S, IQ1_M, IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S, IQ4_NL, IQ4_XS), or BitNet's I2_S as an i2_s_weights where the pinned core has them, over device memory: upload the blocks into a device_buffer and point the view at it. NF4's scale_mean is a host float, as in core.

// The kernels, compiled once; the training backend carries them
auto built = gpu::cuda_quant_kernels::create(*context);
if (built.is_err()) {
std::printf("cuda_quant demo: FAILED - the quantised kernels did not compile\n");
return 1;
}
const auto quant = std::move(built).unwrap();
gpu::cuda_training_backend device{{context.get(), gpu::cuda_math::float32}, ops.get()};
device.quant = quant.get();
// The Q4_0 blocks in device memory, and core's view over them
gpu::device_buffer<ml::block_q4_0> on_device(*context, blocks.size());
on_device.upload(blocks);
const ml::quantized_weights<ml::block_q4_0> q4{on_device.span(), rows, cols};
gpu::device_buffer<float> dx_in(*context, x.size()), ys(*context, n * rows), y1(*context, rows), yq(*context, rows), dyd(*context, dy.size()),
dx(*context, n * cols), ys_tc(*context, n * rows);
dx_in.upload(x);
dyd.upload(dy);
dx.upload(std::vector<float>(n * cols, 0.0f));
const std::span<const float> xs(dx_in.span()), x1 = xs.first(cols);
gpu::linear_sequence(device, q4, x1, y1.span()); // decode: one token
gpu::linear_sequence(device, q4, xs, ys.span()); // prefill: 64 tokens, CUDA cores
gpu::linear_sequence_backward_input(device, q4, std::span<const float>(dyd.span()), dx.span()); // the input's gradient
gpu::linear_sequence_q8(device, q4, x1, yq.span()); // Q8_0 activations, ggml's dot products
gpu::cuda_training_backend tensor = device;
tensor.math = gpu::cuda_math::bf16;
gpu::linear_sequence(tensor, q4, xs, ys_tc.span()); // prefill on the tensor cores

Relationships. cuda_ops.hpp (cuda_training_backend, which carries quant), cuda.hpp (the context and device_buffer), opencl_quant.hpp (the same kernels and tests on OpenCL), core's ml/linear.hpp, ml/nf4.hpp, ml/quantize.hpp, ml/lora.hpp. Group: snicholls-gpu.

Implementations. As opencl_quant.hpp: matrix-vector kernels for at most cuda_quant_kernels::matvec_max rows (a block of 64 threads per four outputs, a fixed reduction tree), the tiled kernel (64 x 64 tiles, each output summed in index order), the Q8_0 path (core's terms added in block order). Under cuda_math::bf16 the tiled products run on the tensor cores instead: each 64 x 64 tile's weights dequantised and rounded to bfloat16 into shared memory as they are loaded, the activations rounded likewise, mma.sync m16n8k16 with float accumulators.

Guarantees. Every kernel is queued on the context's stream and none waits; nothing is atomic, so every result is the same every run.

operation against bound
tiled, cuda_math::float32 or tf32 core's reference product over the dequantised weights to the bit

| tiled, cuda_math::bf16 | the same | |Δ| ≤ 2^-7 Σ_j |w_j x_j| per output (both operands rounded to bfloat16) | | matrix-vector | the same | |Δ| ≤ k 2^-23 Σ_j |w_j x_j| per output | | Q8_0 activations | ml::linear(w, prepare_input(w, x), y, bias) | to the bit |

The Q8_0 path keeps its quantised activations in working space of the kernels object between calls, so one cuda_quant_kernels serves one stream at a time, as cuda_moe_kernels does.

Errors. create returns a cuda_failure if the kernels do not compile (the log on stderr). A shape the format does not allow or spans of the wrong size throw std::invalid_argument; Q8_0 activations over another format, std::invalid_argument; a backend without quant, std::logic_error; a failed launch, cuda_exception.

Performance. benchmarks/cuda_quant_benchmark.cpp: decode bandwidth and prefill rate against dequantising to float and multiplying with cuBLAS. Not yet measured: the numbers wait for a free GPU.

Tests and demos. tests/cuda_quant_test.cpp (the suite opencl_quant_test.cpp passes, support/quant_suite.hpp, under each math; a QLoRA layer through core's lora_sequence), demos/cuda_quant_demo.cpp.

Dependencies. cuda_ops.hpp, detail/quant_source.hpp, <nvrtc.h>, core's ml/linear.hpp, ml/nf4.hpp, ml/quantize.hpp, ml/minifloat.hpp.

Known issues. BitNet's TL1 and TL2 are lookup-table tilings of the same ternary weights shaped for CPU SIMD kernels; on a device the weights are read as I2_S. The integer path uses int32 multiply-adds, not dp4a (the blocks are 2-byte aligned) or the integer tensor cores; the matrix-vector kernels read bytes. Both are the next steps for speed.

Status. Experimental, new in 0.9.0.

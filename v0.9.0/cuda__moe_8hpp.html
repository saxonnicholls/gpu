Detailed Description

snicholls::gpu::cuda_moe_kernels: snicholls-core's mixture-of-experts steps (ml/moe.hpp) on an NVIDIA GPU, so an MoE transformer trains with its routing, permutation, grouped products and balance losses on the device.

Overview. Core's mixture of experts (TRAINING.md T10) makes every step a free function taking the backend first: routing, the histogram and its prefix sum, the stable permutation, gather and combine, the grouped products and the balance terms. This header overloads each for cuda_training_backend (found by argument-dependent lookup), so with the router logits, the experts' weights and every activation in device_buffers, core's ml::moe_forward and ml::moe_backward run on the GPU; the experts' activations are cuda_ops.hpp's fused kernels over the permuted rows, the router and the shared experts its dense products.

  • cuda_moe_kernels::create(context): compiles the kernels for the context's device (NVRTC); result with a cuda_failure.
  • backend.moe = moe_kernels.get(): the training backend carries a pointer to them; an overload here throws std::logic_error on a backend without one.
auto ctx = gpu::cuda_context::create();
if (ctx.is_err()) {
std::printf("cuda_moe demo: FAILED - no CUDA device\n");
return 1;
}
const auto context = std::move(ctx).unwrap();
auto dense = gpu::cuda_kernels::create(*context); // the dense steps: products, norms, activations
auto moe = gpu::cuda_moe_kernels::create(*context); // routing, the permutation, the grouped products, the balance terms
if (dense.is_err() || moe.is_err()) {
std::printf("cuda_moe demo: FAILED - the kernels did not compile\n");
return 1;
}
const auto kernels = std::move(dense).unwrap();
const auto moe_kernels = std::move(moe).unwrap();
gpu::cuda_training_backend device{{context.get()}, kernels.get()};
device.moe = moe_kernels.get();
// The layer's parameters, its selection bias, its input, and every buffer core's sizes say
tensor<float> params(*context, wave(ml::moe_parameter_count(c), 0.2f, 0.0f)), bias(*context, wave(c.experts, 0.05f, 1.0f)),
xs(*context, wave(rows * d, 1.0f, 2.0f)), ys(*context, std::vector<float>(rows * d)), values(*context, std::vector<float>(ml::moe_activation_values(c, rows))),
dys(*context, wave(rows * d, 1.0f, 3.0f)), dxs(*context, std::vector<float>(rows * d)), grads(*context, std::vector<float>(ml::moe_parameter_count(c))),
work(*context, std::vector<float>(ml::moe_gradient_work(c, rows)));
tensor<std::uint32_t> indices(*context, std::vector<std::uint32_t>(ml::moe_activation_indices(c, rows)));
auto pass = [&](const auto& backend, bool on_device) {
auto s = [&](auto& t) { return on_device ? t.dev->span() : std::span(t.host); };
const auto w = ml::moe_weights_in<c>(std::span<const float>(s(params)), std::span<const float>(s(bias)));
const auto act = ml::moe_activations_in<c>(s(values), s(indices), rows);
const auto losses = ml::moe_forward<c>(backend, w, std::span<const float>(s(xs)), s(ys), act, sequences);
ml::moe_backward<c>(backend, w, std::span<const float>(s(xs)), act, std::span<const float>(s(dys)), s(dxs),
ml::moe_gradients_in<c>(s(grads), s(work), rows), sequences);
return losses;
};
const auto on_gpu = pass(device, true); // every step on the device
const auto on_host = pass(snicholls::linalg::reference, false); // core's reference

The steps on the device.

step kernel against core's reference
moe_route_rows a thread per row: the affinities, core's insertion top-K over the keys, the weights the experts to the bit away from ties within rounding of the affinities; the weights within rounding (the device's expf)
moe_route_rows_backward a thread per row, the weights recomputed within rounding
moe_count_rows, moe_offsets a shared-memory histogram per block (integer atomics: exact, order-free), the prefix sum to the bit
moe_permutation a counting sort: each block's histogram of its chunk, each expert's start in each chunk, then each block ranks its pairs tile by tile (warp match_any, the warps in order) to the bit (the order is unique)
moe_gather_rows, its backward a thread per value (float4 where aligned); the backward adds the K slots in slot order to the bit
moe_combine_rows, its backward a thread per value in slot order; dweights a thread per pair summing its row in element order to the bit
grouped_linear, its backward one launch per product over every expert (below) within the product's rounding
moe_update_bias a thread per expert, the sign in 64-bit integers to the bit
moe_balance_loss, moe_z_loss the probabilities a thread per row, the sums per (group, expert) in row order, the loss in core's order within rounding (expf, logf)
moe_send_offsets, moe_receive_offsets, moe_receive_layout expert parallelism's layouts from every rank's counts in device memory to the bit
moe_all_to_all, moe_permute_rows, moe_unpermute_rows in-process ranks on one device, a thread per element, any 1-, 2-, 4- or 8-byte payload to the bit
to_bfloat16_rows, to_float_rows a thread per value, core's rounding (a NaN kept quiet with its sign) to the bit

The experts' activations are cuda_ops.hpp's mlp_activate_rows and its backward over the permuted rows, the router and the shared experts its dense products; so core's ml::moe_forward, ml::moe_backward and the block of ml/moe_block.hpp (block_forward_sequence, block_backward) run on the device unchanged.

The grouped products. The segments' sizes come from the routing, so they are known only on the device. grouped_linear and its backward run as one kernel each (grouped_path::kernel, the default): the segments' bounds are read from the offsets in device memory, the grid sized from the rows (an upper bound of rows / 128 + E row tiles; a block past the last segment returns), 128 x 128 tiles on the tensor cores with float accumulators: mma.sync m16n8k8 in TF32 under cuda_math::tf32, m16n8k16 in bfloat16 under cuda_math::bf16 (the operands rounded as they are loaded, no conversion pass), and under cuda_math::float32 three TF32 products per tile (the operands split into a TF32 part and the remainder, the small-times-small term dropped), which is float's accuracy. The weight gradient's reduction runs over a segment's rows in order inside one block, so nothing is atomic and the result is the same every run. Nothing waits for the host, so a whole MoE forward and backward pass can be captured as a cuda_graph. grouped_path::cublas instead copies the offsets to the host (one wait per call) and makes each expert's product through cuBLAS, as core's reference loops them; it cannot be captured.

Losses in a graph. moe_balance_loss and moe_z_loss return a number. Outside a capture they wait for it; during a capture (or with cuda_moe_kernels::losses_on_device) they write it to cuda_moe_kernels::losses() (the balance loss at 0, the z-loss at 1), return a quiet NaN, and the gradient is unaffected.

Relationships. cuda_ops.hpp (the backend, the activations, the dense products), cuda.hpp (the context, device_buffer, cuda_graph), core's ml/moe.hpp (the operations it overloads and the reference it is checked against). Group: snicholls-gpu.

Guarantees. Every step is queued on the context's stream; none waits, except the two losses outside a capture and grouped_path::cublas. Every kernel is deterministic: two runs give the same bits. The kernels' working space is kept between calls; run a step once uncaptured before capturing it, so the space has its size.

Errors. cuda_moe_kernels::create returns a cuda_failure if the kernels do not compile. An overload throws std::logic_error if the backend has no moe kernels, std::invalid_argument past the device's limits (more than 1024 experts), cuda_exception if a launch fails.

Performance. benchmarks/cuda_moe_benchmark.cpp, docs/performance.md. On an RTX PRO 4000 Blackwell (CUDA 13.3, Release, 2026-11-19) while another training job kept the GPU fully busy, so upper bounds and noisy: the grouped up projection of 4096 tokens of 768 (eight experts of 2048, two per token) forward in 3.8 ms in TF32 against 3.5 ms for cuBLAS expert by expert and 3.4 ms for cublasGemmGroupedBatchedEx; in bfloat16 3.3 ms against 2.9 ms; in float 7.5 ms against 7.7 ms. With 64 experts of 256 (eight per token, 32768 rows) the kernel matches or beats cuBLAS's loop in every math (float 4.0 ms against 6.9). cuBLASLt's grouped matrix layouts are not supported on this device (sm_120).

Tests and demos. tests/cuda_moe_test.cpp (each step against core's reference on the host, the edge cases, two runs bit for bit, whole MoE layers and an MoE block forward and backward, a captured graph, expert parallelism's layouts and payloads), demos/cuda_moe_demo.cpp:

const auto act = ml::moe_activations_in<c>(values.dev->span(), indices.dev->span(), rows);
gpu::moe_update_bias<c>(device, act.counts, bias.dev->span());
const auto grads_before = grads.back(), dxs_before = dxs.back();
moe_kernels->losses_on_device = true;
auto made = gpu::cuda_graph::capture(*context, [&] { pass(device, true); });
moe_kernels->losses_on_device = false;

Dependencies. cuda_ops.hpp, <nvrtc.h>, core's ml/moe.hpp, ml/moe_block.hpp, ml/expert_parallel.hpp, ml/minifloat.hpp.

Known issues. Float only (the payload rows also in bfloat16). At most 1024 experts and 64 ranks. The selection is decided on affinities the device computes with its own expf, so two keys within an ulp of each other may be ordered differently from the host's.

Status. Experimental, new in 0.8.0.
